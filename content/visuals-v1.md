# Visual protocol · v1

Use a visual when it adds understanding. A text-only post is a valid choice: set `visualPreference` to `none`. Never force a generic illustration onto every card.

Prefer a readable source photo, simple diagram, or single plot when its actual preview has been inspected. Captions alone are insufficient. Keep attribution and a source link. Preserve the existing bounded image-fetch and allowed-source checks. Reject dense panels, collages, tiny labels, architecture charts, and images whose meaning cannot be understood at feed width.

Otherwise choose a subject-specific conceptual illustration: surface hexagons, a robot arm, an audio event, road sensors, a video player, a phone, shared documents, or a drawer and its movement axis. Network, layers, orbit, pipeline, and qualitative comparison layouts remain available when they represent the subject. Use 1–3 short labels and an honest caption.

Concept art must be labelled as an illustration. Its geometry does not encode measured values. Do not fabricate bars, curves, time series, trajectories, result screenshots, or “before and after” outcomes. A data redraw requires verified values and units plus separate review; the conceptual renderer deliberately has no data-chart input.

Review the feed as a sequence. Avoid adjacent repeated compositions and repeated three-step diagrams. Change the visual idea before changing only its accent. If a source image fails, use its safe conceptual fallback unless the card explicitly requests no visual.

The bundled demo is manually curated from its stored abstracts. Refresh scripts can generate draft copy and inspect source images, but an update still needs evidence and feed-level visual review. Keep live rendering local and immediate; image generation is not a prerequisite for reading a post.
